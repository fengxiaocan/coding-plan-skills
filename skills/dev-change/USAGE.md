# Dev Change 使用文档

## 用途

`dev-change` 用于**任务完成后自动生成变更记录文档**（CHANGELOG），用于项目归档、问题追踪、代码审计、后续维护和新成员交接。

**核心理念**：任务完成不是终点，变更记录是项目资产。

---

## 触发方式

在 Claude Code 对话中输入：

```
/dev-change
```

或在开发任务完成后由 AI 自动触发。

---

## 输出文件

自动保存到项目 `docs/` 目录：

```
docs/CHANGELOG-YYYY-MM-DD.md
```

- 例：`docs/CHANGELOG-2026-06-11.md`
- 当天已存在时自动递增版本：`CHANGELOG-2026-06-11-v2.md`

---

## 文档结构（10 章节）

| 章节 | 内容 | 要求 |
|------|------|------|
| 1. 修改概述 | 任务目标、解决的问题、修改原因 | 3~10 行，外行也能懂 |
| 2. 需求来源 | 用户需求、目标结果 | — |
| 3. 修改范围 | 文件列表及修改类型 | 新增/修改/删除/重构 |
| 4. 核心实现说明 | 修改前后对比、设计决策 | 解释思路，不复制代码 |
| 5. 关键函数说明 | 新增/重要修改函数 | 作用、输入输出、调用关系 |
| 6. 配置变更 | Gradle/CMake/Manifest 等变更 | 无则写「无配置变更」 |
| 7. 影响范围分析 | 直接/间接影响、风险、兼容性 | — |
| 8. 验证记录 | 编译/测试/功能/回归验证结果 | 失败必须写明原因 |
| 9. 回滚方案 | 出问题时的回退策略 | — |
| 10. 后续优化建议 | 技术债务、优化方向 | 可选，不混入本次交付 |

## 使用示例

### 示例 1：任务完成后生成

**用户输入：**
```
/dev-change 我已经完成了深色模式的开发，帮我生成变更记录
```

**AI 响应：**
```
已生成本次变更记录：

## 修改总结
添加了深色模式切换功能，支持跟随系统和手动切换两种方式。

## 验证结果
- 编译通过：是
- 功能验证通过：是
- 回归测试通过：是

## CHANGELOG文件路径
`docs/CHANGELOG-2026-06-11.md`

## 待确认事项
无
```

### 示例 2：查看当前变更状态

**用户输入：**
```
/dev-change 看看这次改了哪些文件
```

**AI 响应：**
```
检测到以下变更文件：

| 文件 | 类型 | 修改内容 |
|------|------|----------|
| src/theme/ThemeProvider.tsx | 修改 | 添加深色模式状态管理 |
| src/theme/dark.ts | 新增 | 深色主题配色方案 |
| src/components/ThemeToggle.tsx | 新增 | 主题切换开关组件 |

正在生成 CHANGELOG...
```

## 诚信规则

| 规则 | 说明 |
|------|------|
| 禁止编造 | 未验证的内容不得写「通过」 |
| 禁止猜测 | 不确定的内容标记为「无法确定」 |
| 禁止省略 | 失败的验证必须写明原因 |
| 信息不足时 | 标记为 【未验证】/【待确认】/【无法确定】 |

## 何时使用

- [x] 功能开发完成后
- [x] Bug 修复完成后
- [x] 代码重构完成后
- [x] 需要生成项目文档时
- [x] 代码审计前

---

## 注意事项

1. **确保 git 有记录**：`dev-change` 依赖 git diff 获取变更信息，请确保已提交或暂存修改
2. **验证结果如实填写**：如果测试未跑完，请标记为【未验证】
3. **配置变更别遗漏**：涉及构建配置、权限配置等容易被忽略
4. **回滚方案要实用**：考虑清楚哪些文件需要回滚，避免遗漏依赖项
5. **后续建议独立成章**：不要混到本次交付内容里
