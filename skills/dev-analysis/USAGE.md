# Dev Analysis 使用文档

## 用途

`dev-analysis` 用于**分析已有代码功能，生成可长期维护的功能说明文档**。适用于学习代码、补充文档、项目交接、新成员培训、功能梳理。

**核心理念**：只理解、只解释、只沉淀，不评价、不建议、不修改。

---

## 触发方式

在 Claude Code 对话中输入：

```
/dev-analysis
```

或明确请求分析某个功能/模块，例如：

- "帮我分析一下游戏扫描功能"
- "整理一下 ROM 识别模块的文档"
- "我想理解 Moonlight 串流这块代码"

---

## 输出文件

自动保存到项目 `docs/` 目录：

```
docs/{模块名}/README.md
```

- 例：`docs/game-scan/README.md`
- 如果 README.md 已存在，保存为 `README-v2.md` 或询问用户是否更新原文档

---

## 工作流程（3 阶段）

```
阶段 1: 需求确认 → 确认功能范围、代码位置、分析目标、输出位置
阶段 2: 代码阅读 → 分析模块结构、调用关系、数据流、配置依赖
阶段 3: 文档生成 → 按模板生成功能说明文档并保存
```

---

## 阶段 1：需求确认

每次最多提出 3 个问题，信息不足时继续提问，直到可以开始分析。

### 需要确认的信息

| 类别 | 示例 |
|------|------|
| 功能范围 | 游戏扫描 / ROM 识别 / OCR 翻译 / 输入映射 / Moonlight 串流 |
| 代码位置 | `app/src/main/java/...` / `native/src/...` / `feature/game/` |
| 分析目标 | 学习代码 / 补充文档 / 项目交接 / 新成员培训 / 功能梳理 |
| 输出位置 | `docs/game-scan/` / `docs/ocr/` / `docs/moonlight/` |

---

## 阶段 2：代码阅读

重点分析以下四个方面：

### 模块结构

- 目录结构
- 模块关系
- 文件职责

### 调用关系

- 入口
- 调用链
- 关键对象
- 核心流程

### 数据流

- 输入来源
- 数据处理
- 输出结果
- 状态变化

### 配置依赖

- 配置文件
- 参数
- 资源文件
- 第三方依赖

---

## 阶段 3：文档生成

按照 [TEMPLATE.md](TEMPLATE.md) 生成标准功能文档，包含以下章节：

| 章节 | 内容 |
|------|------|
| 功能概述 | 解决什么问题，用户获得什么能力 |
| 模块位置 | 目录、模块、主要文件 |
| 整体架构 | 主要组件及关系 |
| 核心流程 | 步骤化描述 |
| 调用链分析 | 入口函数、核心函数、结束位置、调用关系 |
| 数据流分析 | 输入、处理、输出、状态变化 |
| 关键类说明 | 作用、职责、调用关系 |
| 关键函数说明 | 作用、参数、返回值、调用时机 |
| 配置说明 | 配置文件、关键参数、默认值、用途 |
| 对外接口 | API / Service / Binder / JNI / Callback |
| 使用场景 | 用户操作流程、触发条件、执行结果 |
| 时序说明 | 触发 → 处理 → 结果 |
| 总结 | 模块职责与项目定位 |

## 文件结构

```
skills/dev-analysis/
├── SKILL.md      # 技能定义（Claude Code 元数据 + 行为指令）
├── README.md     # 快速入口
├── USAGE.md      # 使用文档（本文件）
└── TEMPLATE.md   # 文档模板
```

| 文件 | 用途 |
|------|------|
| [SKILL.md](SKILL.md) | 定义 Skill 元数据、触发条件、核心原则与工作流程 |
| [README.md](README.md) | 快速入口：命令、用途、规则一览 |
| [USAGE.md](USAGE.md) | 完整使用说明、示例、全局规则 |
| [TEMPLATE.md](TEMPLATE.md) | 标准化输出文档结构 |

## 使用示例

### 示例 1：分析游戏扫描功能

**用户输入：**

```
/dev-analysis 帮我分析一下游戏扫描功能
```

**AI 响应（阶段 1）：**

```
好的，我来帮您分析游戏扫描功能。先确认几个信息：

1. 这个功能在哪个目录？（例如 app/src/main/java/com/example/scan/）
2. 您的分析目标是什么？（学习代码 / 补充文档 / 项目交接 / 新成员培训 / 功能梳理）
3. 文档希望输出到哪个目录？（例如 docs/game-scan/）
```

### 示例 2：整理 ROM 识别模块文档

**用户输入：**

```
/dev-analysis 整理一下 ROM 识别模块的文档
```

**AI 响应（阶段 1）：**

```
好的，我来整理 ROM 识别模块的文档。

1. ROM 识别相关代码在哪个目录？
2. 该模块是否有外部依赖？（如数据库、网络接口、本地文件等）
3. 输出文档是否保存到 docs/rom-identifier/？
```

## 全局规则

| 规则 | 说明 |
|------|------|
| 每轮最多 3 个问题 | 逐步推进，不一次性 overwhelm 用户 |
| 禁止跳过阶段 | 必须按顺序完成 1→2→3 |
| 禁止提前分析 | 未确认需求前不得直接打开代码 |
| 禁止编造 | 不得虚构不存在的逻辑 |
| 禁止评价 | 不得输出 Bug/风险/债务/质量/重构/优化建议 |
| 标记不确定性 | 无法确认的信息标记为 【待确认】/【代码中未发现】 |
| 文档必须保存 | 分析结果必须输出到 docs/{模块名}/README.md |

## 注意事项

1. **明确边界**：本 Skill 不审查代码、不找 Bug、不提优化建议
2. **以代码为准**：所有内容必须基于实际代码，不能猜测
3. **文档结构统一**：使用 [TEMPLATE.md](TEMPLATE.md) 保持风格一致
4. **保留不确定性**：无法确认的内容用 【待确认】 或 【代码中未发现】 标注
5. **保存后告知**：文档保存后向用户输出已分析文件、保存位置、功能摘要
