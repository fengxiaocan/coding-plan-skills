# Fix Plan 使用文档

## 用途

`fix-plan` 用于**修复 Bug、排查异常、分析故障、定位问题**时，强制要求 AI 先完成信息收集，再进入分析和修复阶段。

**核心理念**：禁止猜测、禁止提前编码、必须基于证据进行诊断。

---

## 触发方式

在 Claude Code 对话中输入：

```
/fix-plan
```

或描述问题时 AI 自动触发（当检测到 bug/错误/异常等关键词时）。

---

## 工作流程（7 阶段）

```
阶段 1: 确认问题    → 收集期望行为、实际行为、错误表现、复现稳定性
阶段 2: 收集环境    → 收集 OS、版本、编译环境、部署方式
阶段 3: 收集复现步骤 → 收集完整步骤、触发条件、最短复现路径
阶段 4: 收集证据    → 索要日志、Stack Trace、配置文件、相关代码
阶段 5: 整理问题说明 → 输出问题摘要，等待用户确认
阶段 6: 原因分析    → 输出根因、证据链、修复方案、风险点、验证方案
阶段 7: 开始修改    → 满足全部条件后才能写代码
```

---

## 使用示例

### 示例 1：报告应用崩溃

**用户输入：**
```
/fix-plan 我的 App 启动时崩溃了
```

**AI 响应（阶段 1）：**
```
为了更好地诊断这个问题，我需要了解几个信息：

1. 崩溃时有什么错误提示或弹窗信息吗？
2. 这个问题是每次启动都会发生，还是偶尔发生？
3. 大概什么时候开始出现这个问题的？

---
当前阶段：第 1 阶段 — 确认问题
已收集：App 启动时崩溃
待收集：错误表现、复现稳定性、出现时间
```

### 示例 2：编译报错

**用户输入：**
```
/fix-plan 编译报错了，帮忙看看
```

**AI 响应（阶段 1）：**
```
好的，我来帮您排查编译问题。

1. 具体的编译错误信息是什么？可以贴一下报错内容吗？
2. 这个错误是最近才出现的，还是之前编译正常？
3. 您期望的编译结果是什么？
```

## 全局规则

| 规则 | 说明 |
|------|------|
| 每轮最多 3 个问题 | 逐步收集，不一次性 overwhelm 用户 |
| 禁止跳过阶段 | 必须按顺序完成 1→2→3→4→5→6→7 |
| 禁止猜测 | 不得在无证据时推断原因 |
| 禁止提前编码 | 未到阶段 7 不得写任何修复代码 |
| 需要用户确认 | 进入下一阶段前必须得到确认 |

---

## 何时使用

- [x] 应用崩溃或异常退出
- [x] 编译/构建失败
- [x] 功能不符合预期
- [x] 性能问题
- [x] 逻辑错误
- [x] 任何需要修复的问题

---

## 注意事项

1. **耐心配合**：信息收集可能需要多轮对话，请尽量提供详细信息
2. **提供证据**：日志、截图、错误信息越详细越好
3. **确认节点**：阶段 5 的问题摘要需要您确认后才继续分析
4. **不要催促编码**：未完成信息收集前，AI 会拒绝写代码
